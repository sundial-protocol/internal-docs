# Sundial's Security Practices

Sundial uses industry-standard best practices across all repositories, with a focus on defense-in-depth, least privilege, and fail-closed defaults. The following sections summarize the key security measures implemented in each repository, as well as how they work together to secure the overall protocol.

## How the Repositories Work Together

`btc-locker` is a TypeScript library that constructs and validates Bitcoin transactions — it defines the on-chain rules: what scripts are valid, what keys are required, and what spending conditions must be met. `btc-yield` is the off-chain system (API + indexer) that orchestrates the yield protocol on top of those rules. The indexer watches the Bitcoin chain for transactions matching `btc-locker`'s Tapscript patterns and validates them against the protocol state stored in its database; the API exposes endpoints for providers and users to submit PSBTs and manage their positions. Neither system is independently sufficient — `btc-locker` enforces what is cryptographically possible, and `btc-yield` enforces the protocol rules on top of that. An attacker who bypasses the API still cannot spend funds without satisfying the on-chain script conditions defined by `btc-locker`, and an attacker who constructs a valid script spend still cannot manipulate the protocol state without also bypassing `btc-yield`'s indexer validation.

`sundial-monorepo` is the primary project and contains the Cardano L2 (Midgard) — the on-chain Aiken/Plutus V3 validators, the Haskell off-chain transaction library, the TypeScript node and SDK, and the AWS deployment infrastructure. The other repositories are developed independently and pulled into `sundial-monorepo` as git submodules, allowing the L2 to reference pinned, audited versions of each component without absorbing their full development history. The submodule boundaries also mean that each sub-project can maintain its own CI, dependency graph, and release cadence while the monorepo's top-level workflows target only the native L2 code.

## btc-locker

- **Protocol-level security via Bitcoin Script:** Funds are locked in P2WSH outputs encoding two spend paths — an absolute timelock (`OP_CHECKLOCKTIMEVERIFY`) and a relative timelock (`OP_CHECKSEQUENCEVERIFY`) for depositor recovery, and an `OP_IF`/`OP_ELSE` escrow script requiring the counterparty key before the deadline. Neither party can spend unilaterally outside their designated path.
- **Key management & cryptography:** `KeyPair` and `keys.ts` enforce secp256k1 validity and PSBT-based signing so private keys never touch transaction construction directly.
- **Input validation:** `validation.ts` covers network-aware address checksum/format checks, pubkey hex, satoshi bounds, and locktime ranges — all with dedicated test coverage.
- **Trust model:** Formal threat assumptions and per-party capability boundaries are documented in `spec/v0/trust-model.md`.
- **Known gap (demo only):** The demo server's keypair generation/import endpoints are explicitly flagged as requiring authentication before production use.

## btc-yield

- **Structured audit program:** Five sequential third-party audits (Mar–Apr 2026) with tracked Critical-to-Medium findings and corresponding fix commits, covering on-chain validation gaps, credential exposure, and API authorization failures.
- **On-chain validation:** The indexer's transaction processor enforces canonical outpoint spending for provider-claims (H-5-01), withdrawal destination/amount binding (H-5-02), strict 1:1 output-to-allocation mapping with an AML invariant (C-5-01), and explicit deposit outpoint validation to block attacker-controlled outputs (H-5-03).
- **API input validation:** NestJS global `ValidationPipe` is configured fail-closed (`forbidNonWhitelisted: true`). DTOs enforce UUID formats, numeric bounds, and PSBT semantic validation. Configs reject missing required env vars at startup rather than falling back to unsafe defaults (M-5-04).
- **Secret management:** Runtime secrets injected via AWS Secrets Manager (replacing insecure Docker `ARG` patterns). CI uses AWS OIDC federation to eliminate long-lived credentials. Runtime env scripts guard against leaking sensitive variable names at output.
- **Static analysis pipeline:** GitHub Actions runs Semgrep, Gitleaks, CodeQL (fails at security-severity ≥ 4.0), Trivy, NPM Audit, and OSV on every push — all also runnable locally.
- **Infrastructure hardening:** Terraform provisions VPC public/private subnet isolation, security groups scoping inbound access to ALB/RDS/Bitcoin node, TLS via ACM/ALB HTTPS listeners, and RDS encryption-at-rest with credentials from Secrets Manager.

## sundial-monorepo (L2 only)

- **Multi-environment Terraform with remote state locking:** Infrastructure for the Midgard node is fully defined in Terraform (`infra/aws/terraform/platform/`). Each environment (testnet, mainnet) has a separate `.tfvars` file and an S3 backend config with DynamoDB state locking (`encrypt = true`), preventing concurrent applies and ensuring state files are encrypted at rest.
- **VPC isolation with private subnets:** The node, database, and EFS volume all run in private subnets with no public IP assignment (`map_public_ip_on_launch = false`). Only the ALB sits in the public subnets. Security groups are scoped to the minimum required: the ALB accepts HTTPS/80 from the internet and forwards only to ECS dynamic ports; RDS and EFS accept connections only from the ECS security group.
- **All secrets via AWS Secrets Manager — never in task environment variables:** Every sensitive value (RDS password, operator seed phrases for block commitment and merge, Blockfrost/Ogmios/Kupo API keys, Grafana admin password, genesis wallet seed phrases) is stored as a named Secrets Manager secret and injected into the ECS task via the `secrets` field, not `environment`. The Terraform `secrets.tf` enumerates all ARNs explicitly and grants the task execution role `secretsmanager:GetSecretValue` only for those resources.
- **TLS enforced end-to-end via ACM + ALB HTTPS listener:** ACM issues a DNS-validated certificate for each environment domain (e.g. `sundial-node.sundialprotocol.com`). The ALB HTTPS listener is the sole public entry point; HTTP is either redirected or used only for ALB health-check bootstrapping.
- **ALB access logs written to a private, encrypted S3 bucket:** The ALB logs bucket has server-side AES-256 encryption, all public access blocked (`block_public_acls`, `block_public_policy`, `restrict_public_buckets`), and an IAM bucket policy scoped to the ELB log delivery service principal only.
- **CloudWatch log groups encrypted with a dedicated KMS key with rotation enabled:** ECS container logs are routed to a CloudWatch log group (`awslogs` driver) whose KMS key has `enable_key_rotation = true` and a deletion window. The key policy grants `logs.{region}.amazonaws.com` only the encrypt/decrypt permissions it needs.
- **ECS with Container Insights and SSM access (no bastion):** The ECS cluster has `containerInsights = enabled`. ECS host instances are granted `AmazonSSMManagedInstanceCore` rather than SSH access, so operators can open interactive sessions via SSM Session Manager without opening port 22 or managing key pairs.
- **EFS Merkle-Patricia-Trie storage encrypted at rest with a dedicated KMS key:** The node's on-disk MPT state (ledger and mempool) is stored on an EFS file system with `encrypted = true` and a per-resource KMS key. The EFS access point enforces a fixed POSIX UID/GID (1000) and a `0755` root directory, preventing the container from running as root or accessing paths outside its mount.
- **Multi-AZ RDS with deletion protection and final snapshots:** The production (mainnet) RDS instance is configured `multi_az = true`, `deletion_protection = true`, `skip_final_snapshot = false`, and a 7-day backup retention period. Testnet uses a reduced profile but retains deletion protection and a final snapshot identifier to guard against accidental drops.
- **Fail-closed production config validation:** The `midgard-node` service config layer (using the Effect `Config` module) distinguishes `NODE_ENV=production` from development. In production, every required variable is a hard failure with a descriptive error; empty strings are rejected explicitly. Development falls back to safe defaults so the node can start without a full secrets setup.
- **Docker image built with a multi-stage non-root Dockerfile:** The production image uses a `build` stage to compile and prune to production dependencies, then copies only the built artifacts into a `final` stage that runs as the `node` user (`USER node`) with `NODE_ENV=production`. No dev dependencies, build tools, or source files are present in the shipped image.
- **Observability stack co-deployed alongside the node:** Prometheus (scraping the node's `/metrics` endpoint on port 9464 and cAdvisor), Loki, Grafana Alloy (Promtail), Grafana, and Tempo are deployed as a separate ECS task with Cloud Map private DNS service discovery (`prometheus.internal`, `loki.internal`, etc.), keeping the observability plane reachable internally but never exposed to the internet. Retention is environment-scoped (3 days on testnet, 14 days on mainnet).
- **CI security pipeline on every PR:** GitHub Actions runs Gitleaks (secret scanning, with a tuned `.gitleaks.toml` allowlist for known false-positive log paths), Trivy (container and dependency CVE scanning), `pnpm security:audit:all`, and OSV Scanner. All workflows carry `permissions: contents: read` and use concurrency groups to cancel superseded runs. Separate format, lint, type-check, and build jobs run in a matrix with change detection to avoid unnecessary work.
- **L1 node bootstrapped via Mithril-verified chain snapshots:** The `l1-services` Compose stack downloads a Cardano chain snapshot through the Mithril client, requiring explicit `GENESIS_VERIFICATION_KEY` and `ANCILLARY_VERIFICATION_KEY` environment variables with no fallback defaults. The node container only starts after the bootstrap service completes successfully (`condition: service_completed_successfully`), preventing the node from running against an unverified or incomplete chain state.
