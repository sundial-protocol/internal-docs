# M5.5 Onchain Optimizations

**Date:** 2026-06-12  
**Branch:** `onchain-benchmarking-sundial`  
**Toolchain:** Aiken v1.1.21, Plutus v3

---

## Overview

The following optimizations were identified and implemented in the Aiken onchain codebase. Benchmarks were written first using `aiken bench` to quantify both baseline costs and the effect of each change. All benchmarks were measured against a fixed random seed (`695010446`).

The Plutus execution model charges two resources per script invocation: **CPU units** (steps) and **memory units** (word allocations). Both are capped per transaction. Script **code size** (bytes in the serialised UPLC program) is an additional on-chain cost not captured by execution unit measurements.

---

## Consolidate authentic-input helper functions

**File:** [lib/midgard/common/utils.ak](https://github.com/sundial-protocol/sundial-monorepo/blob/main/onchain/aiken/lib/midgard/common/utils.ak)

**Change:** Introduced a shared helper (`authentic_input_and_asset_name`) for authentic input extraction and NFT-policy validation, and rewired the public authentic-input helpers to delegate to it.

**Effect:** Removes duplicated `list.at` + NFT validation logic across helper variants. The primary gain is reduced duplication in compiled script logic and easier maintenance.

**Follow-up cleanup:** The first pass of this consolidation left three datum-returning helpers (`get_authentic_input_datum_with_policy_at`, `get_authentic_input_datum_and_asset_name_with_policy_at`, `get_authentic_input_datum_with_nft_at`) re-wrapping the already-extracted input in `Some(...)` purely to pattern-match it back out:

```diff
- expect Some(Input {
+ expect Input {
    output: Output { datum: InlineDatum(input_datum_data), .. },
    ..
- }) = Some(found_input)
+ } = found_input
```

Each site allocated one `Option` constructor and ran one extra match per call. These now destructure the `Input` directly.

**Execution units:** No material per-call execution-unit change is expected from this refactor. In prior regression-guard runs, observed numeric deltas were attributed to benchmark-run variance rather than script-path changes.

The `Some(...)` cleanup above is not covered by any benchmark and needs none: the only benches in `midgard/common/utils.test` are `zip_fold*` and `get_own_hash_*`, none of which reach these helpers. Of the three, two currently have no callers in the tree, and the third (`..._with_nft_at`) is used only by [lib/midgard/scheduler.ak](../../onchain/aiken/lib/midgard/scheduler.ak). The hub-oracle figures reported below are unaffected — that path goes through `utils.get_authentic_input_of`, a different helper.

## Replace `list.find` with `list.at` in `get_own_hash` / `get_own_address`

**File:** [lib/midgard/common/utils.ak](https://github.com/sundial-protocol/sundial-monorepo/blob/main/onchain/aiken/lib/midgard/common/utils.ak)

**Change:** `get_own_hash` and `get_own_address` previously accepted an `OutputReference` and located the matching input using `list.find` with a full equality predicate on each element. The predicate compares a 36-byte record (32-byte tx id + 4-byte output index) at every step. The functions now accept an `input_index: Int` and use `list.at`, which decrements a counter at each step:

```diff
- pub fn get_own_hash(output_reference: OutputReference, txInputs: List<Input>) {
-   expect Some(input) =
-     list.find(txInputs, fn(x) { x.output_reference == output_reference })
+ pub fn get_own_hash(input_index: Int, txInputs: List<Input>) {
+   expect Some(input) = list.at(txInputs, input_index)
    expect Script(hash) = input.output.address.payment_credential
    hash
  }
```

The `OutputReference` import was removed from `utils.ak` as it was used only by these two functions.

**Effect:** Each traversal step no longer performs a 36-byte structural equality check. For a transaction with N inputs, the worst-case cost drops proportionally. The caller is responsible for supplying the correct index (which the Cardano ledger already provides as part of the script context).

**Execution units — before and after:**

| Benchmark | Before mem | Before cpu | After mem | After cpu | Δ mem | Δ cpu |
|---|---|---|---|---|---|---|
| `get_own_hash_front_of_10` (target at index 0) | 133,228 | 37,921,876 | 131,737 | 36,063,764 | −1,491 (−1.1%) | −1,858,112 (−4.9%) |
| `get_own_hash_back_of_10` (target at index 9) | 168,274 | 61,119,168 | 161,149 | 44,669,984 | −7,125 (−4.2%) | −16,449,184 (−26.9%) |

The pre-optimization suite also included a `get_own_hash_expected_back_of_10` bench that simulated the post-change behaviour inline (using `list.at(inputs, 9)` directly without calling `get_own_hash`). It measured mem 161,249 / cpu 44,685,984 — matching the post-optimization `get_own_hash_back_of_10` to within noise, validating the prediction.

The front-of-list case saves ~1.5M cpu (one fewer `OutputReference` equality check: the old `list.find` found a match immediately but still evaluated the predicate once against a 36-byte record). The back-of-list worst case saves ~16.4M cpu (9 `OutputReference` checks eliminated across steps 1–9, plus the final step). Per step eliminated: ~1.83M cpu / ~792 mem.

## Cache `out_ref_to_nonce` result in event authentication

**File:** [lib/midgard/user-events.ak](https://github.com/sundial-protocol/sundial-monorepo/blob/main/onchain/aiken/lib/midgard/user-events.ak)

**Change:** In event authentication flow, the nonce derived from the spent input reference is computed once (`let nonce = out_ref_to_nonce(...)`) and reused for subsequent checks.

**Effect:** Prevents repeated serialization-and-hash work in the same validation path.

**Execution units:** Benchmark guard in `midgard/user_events.test` quantifies the cost of recomputation:

| Benchmark | Memory | CPU |
|---|---|---|
| `out_ref_to_nonce_cost` | 704 | 339,185 |
| `out_ref_to_nonce_called_twice` | 2,677 | 10,079,540 |

Calling `out_ref_to_nonce` twice in-path is ~29.7× higher CPU than the single-call baseline (`10,079,540` vs `339,185 × 2 = 678,370`). Reusing the computed nonce avoids that repeated cost.

## Lean field extraction for the hub oracle datum

**Files:** [lib/midgard/hub-oracle.ak](https://github.com/sundial-protocol/sundial-monorepo/blob/main/onchain/aiken/lib/midgard/hub-oracle.ak) (new helpers), plus call-site rewires in [validators/computation-thread.ak](https://github.com/sundial-protocol/sundial-monorepo/blob/main/onchain/aiken/validators/computation-thread.ak), [lib/midgard/fraud-proofs/common.ak](https://github.com/sundial-protocol/sundial-monorepo/blob/main/onchain/aiken/lib/midgard/fraud-proofs/common.ak), [lib/midgard/user-events.ak](https://github.com/sundial-protocol/sundial-monorepo/blob/main/onchain/aiken/lib/midgard/user-events.ak), and the three user-event spend validators ([deposit](https://github.com/sundial-protocol/sundial-monorepo/blob/main/onchain/aiken/validators/user-events/deposit.ak), [withdrawal](https://github.com/sundial-protocol/sundial-monorepo/blob/main/onchain/aiken/validators/user-events/withdrawal.ak), [tx-order](https://github.com/sundial-protocol/sundial-monorepo/blob/main/onchain/aiken/validators/user-events/tx-order.ak)).

**Change:** The hub oracle datum has 26 fields — 12 policy IDs, 14 `Address` records (each a nested payment/stake credential structure), and a script hash. The existing reader, `hub.get_datum`, does `expect hub_datum: Datum = hub_datum_data`, which recursively **validates every one of those 26 fields**. But nearly all of the ~18 call sites consume only 1–4 fields.

A new reader, `hub.get_datum_fields`, performs the same NFT authentication but returns the datum's raw constructor fields via `builtin.unconstr_fields` **without** validating them. Callers then pull only the fields they use through positional accessors (`hub.state_queue_of`, `hub.deposit_of`, `hub.settlement_of`, `hub.reserve_addr_of`, …), each of which validates just that single field:

```diff
- let hub.Datum { state_queue: state_queue_policy_id, .. } =
-   hub.get_datum(reference_inputs, hub_oracle_script_hash, hub_oracle_ref_input_index)
+ let state_queue_policy_id =
+   hub.get_datum_fields(reference_inputs, hub_oracle_script_hash, hub_oracle_ref_input_index)
+     |> hub.state_queue_of
```

The shared user-event mint path (`user_events.validate_mint`) was likewise switched: its `event_address_getter` now takes `List<Data>` and each caller supplies e.g. `hub.deposit_addr_of` instead of destructuring a fully-parsed `Datum`.

**Safety:** This is sound under the same trust model the codebase already relies on for `unsafe_event_to_key_value_pair` and the settlement/ledger-state coercions: the hub UTxO is NFT-authenticated and its datum shape is fixed at genesis. Only the fields actually read are validated (an absent index fails `expect Some`, a wrong-typed field fails its coercion), so no read path loses a check it depended on. The accessor indices are positionally coupled to the `Datum` field order and documented as such.

**Effect:** Skips recursive validation of the 25 unused fields — most importantly the nested `Address` records — on every hub-datum read across the converted validators.

**Execution units:** Benchmarks in [lib/midgard/hub-oracle.test.ak](https://github.com/sundial-protocol/sundial-monorepo/blob/main/onchain/aiken/lib/midgard/hub-oracle.test.ak). All three build the same sample datum, so the fixed construction cost is common to each and the deltas isolate the read path.

| Benchmark | mem | cpu |
|---|---|---|
| `hub_datum_full_parse` (old path; validates all 26 fields) | 238,804 | 77,257,604 |
| `hub_datum_lean_state_queue` (new path; one low-index field, idx 4) | 38,085 | 10,996,444 |
| `hub_datum_lean_reserve_addr` (new path; worst-case high-index address, idx 23) | 110,459 | 33,235,657 |

Reading a single low-index policy field instead of parsing the whole datum saves **−66,261,160 cpu (−85.8%)** and **−200,719 mem (−84.0%)**. Even the worst case measured — walking to a high-index `Address` field (idx 23) — still saves **−44,021,947 cpu (−57.0%)** and **−128,345 mem (−53.7%)**, because the other 25 fields (including 13 addresses) are never validated. Multi-field callers re-walk the field list per accessor, but each walk is cheap pointer-following against the eliminated per-field structural validation.

**Not yet converted:** `scheduler`, `settlement`, and the `operator-directory` validators still use `hub.get_datum`, either because they consume many fields or because they hand the full `Datum` across a callback boundary. They can be migrated to the accessors incrementally.

## Use already-typed event datum fields instead of re-parsing

**Files:** [validators/user-events/withdrawal.ak](https://github.com/sundial-protocol/sundial-monorepo/blob/main/onchain/aiken/validators/user-events/withdrawal.ak) (both `InitializePayout` and `Refund`), [validators/user-events/tx-order.ak](https://github.com/sundial-protocol/sundial-monorepo/blob/main/onchain/aiken/validators/user-events/tx-order.ak).

**Change:** These spend validators receive their datum as a fully-decoded `Option<Datum>`, so the nested event record (`WithdrawalEvent` / `TxOrderEvent`) — including its `info` / `tx` field — is already typed and validated on entry. The old code nonetheless upcast the event back to `Data`, split it with `unsafe_event_to_key_value_pair`, and then re-ran a structural `expect` to recover the typed field, validating the same bytes a second time:

```diff
- let Pair(withdrawal_event_id, withdrawal_event_info) =
-   ledger_state.unsafe_event_to_key_value_pair(withdrawal_event)
- expect coerced_withdrawal_info: ledger_state.WithdrawalInfo =
-   withdrawal_event_info
+ let ledger_state.WithdrawalEvent { id: withdrawal_id, info: coerced_withdrawal_info } =
+   withdrawal_event
+ let withdrawal_event_id: Data = withdrawal_id
```

The fix reads the typed `id`/`info`/`tx` fields directly. Upcasting a typed field back to `Data` (for the `plutarch_phas` key/value, or for the validity-override record update) is free at runtime — it is the same underlying `Data` — so proof inputs are byte-identical to before.

**Effect:** Removes one `unconstr_fields` split plus a full structural re-validation of the event's `info`/`tx` sub-record per spend. The withdrawal case is the heavier one: `WithdrawalInfo` carries a `WithdrawalBody` (value pairs, address, datum) plus a 64-byte signature.

**Scope note:** Only the spend validators' *own* datums are affected, since only those are pre-decoded by the ledger. `settlement.valid_event_inclusion` and `deposit`'s spend path read event data straight from reference-input `Data`, so their `unsafe_event_to_key_value_pair` usage is a genuine first parse and was left unchanged.

**Execution units:** Benchmarks in [lib/midgard/user-events.test.ak](https://github.com/sundial-protocol/sundial-monorepo/blob/main/onchain/aiken/lib/midgard/user-events.test.ak). Each pair builds the identical sample event and produces the identical overridden `Data`; only the middle step differs (re-parse vs typed field read), so the delta isolates the removed work.

| Benchmark | mem | cpu |
|---|---|---|
| `withdrawal_info_reparse` (old path) | 78,098 | 24,410,293 |
| `withdrawal_info_typed` (new path) | 13,292 | 4,189,809 |
| `tx_order_reparse` (old path) | 19,688 | 6,056,437 |
| `tx_order_typed` (new path) | 7,412 | 2,240,148 |

Removing the withdrawal re-parse saves **−20,220,484 cpu (−82.8%)** and **−64,806 mem (−83.0%)** per spend. The lighter tx-order re-parse (a 3-field `MidgardTxCompact`) saves **−3,816,289 cpu (−63.0%)** and **−12,276 mem (−62.4%)**. The withdrawal validator applies this on both its `InitializePayout` and `Refund` paths.

## Execution-budget regression guard (Plutarch)

**Files:** [onchain/plutarch/tests/Testing/Budget.hs](../../onchain/plutarch/tests/Testing/Budget.hs), wired into the `helpers-tests` suite via [midgard-merkle.cabal](../../onchain/plutarch/midgard-merkle.cabal) and [tests/Test.hs](../../onchain/plutarch/tests/Test.hs).

**Change:** The Aiken side of this milestone is measured with `aiken bench`, which has no Plutarch equivalent. This adds a budget-ceiling test module on the Plutarch side so that execution-unit regressions in the Merkle membership validators fail CI rather than being discovered on-chain.

Each test fully applies a validator to a rewarding-script context built by `Testing.ScriptContextBuilder`, evaluates it via `Profile.getExUnits`, and asserts the result sits under a ceiling. Three cases are covered: `membershipStakeValidator` against two membership proofs (keys `deadbeef` and `cafe`) and `nonMembershipStakeValidator` against a non-membership proof (key `cafe`). The fixtures mirror those in `Testing.MembershipValidator`, so the guard exercises the same proofs the correctness tests do.

**Design note:** the comparison is component-wise rather than a plain `<=` on `ExBudget`. `ExBudget` derives a lexicographic `Ord`, so `actual <= ceiling` would pass whenever CPU is under budget regardless of how far memory overshoots. `withinBudget` checks `exBudgetCPU` and `exBudgetMemory` independently. Failures print the measured budget alongside the ceiling so the limit can be re-tuned from the test output.

**Execution units:** No baselines are recorded here yet. The ceilings are deliberately loose placeholders — 50 % of the Cardano mainnet per-transaction limits (CPU 5,000,000,000 of 10,000,000,000; memory 7,000,000 of 14,000,000) — chosen to catch order-of-magnitude regressions without churn. They should be tightened to just above the measured values once the suite has run in CI and produced real numbers.

| Validator | Case | Ceiling (cpu / mem) | Measured |
|---|---|---|---|
| `membershipStakeValidator` | key `deadbeef` | 5,000,000,000 / 7,000,000 | to be recorded |
| `membershipStakeValidator` | key `cafe` | 5,000,000,000 / 7,000,000 | to be recorded |
| `nonMembershipStakeValidator` | key `cafe` | 5,000,000,000 / 7,000,000 | to be recorded |

**Note:** the module was initially added without being registered in `helpers-tests.other-modules` or included in `Test.hs`, so it did not run. Both are now wired up; a Plutarch test module is inert until it appears in *both* places.
