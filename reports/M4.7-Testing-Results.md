# Testing Results — Staking & DeFi

## Overview

This report summarises the functional test results across the staking and DeFi yield features implemented in `btc-locker` and `btc-yield`. It covers unit, integration, and end-to-end test outcomes as of the May 2026 milestone, as well as coverage metrics and the remediation trajectory observed across four sequential internal audits conducted between March and April 2026.

Bridging is out of scope for this report.

---

## How the Repositories Map to Features

| Feature Area | Primary Repo | Role |
|---|---|---|
| Staking — script construction & spending | `btc-locker` | Constructs timelock / escrow Tapscripts, manages PSBT signing, validates keys and amounts |
| Staking — on-chain lifecycle | `btc-yield / indexer` | Detects and validates deposit, claim, distribution, and withdrawal transactions on-chain |
| DeFi yield — provider/program management | `btc-yield / api` | Exposes REST endpoints for providers, programs, and deposit intents |
| DeFi yield — user staking flow | `btc-yield / api` | Creates and validates user deposit intent PSBTs, tracks due repayments |
| DeFi yield — distribution reconciliation | `btc-yield / indexer` | Reconciles distribution allocations; enforces AML invariant and output binding |

## btc-yield — End-to-End & System Tests

### API E2E (`apps/api/test/e2e/`)

`live-server.e2e.test.ts` spins up a full NestJS application with a real Postgres database and exercises the complete HTTP surface: provider registration, program creation, deposit intent creation and PSBT submission, distribution intent creation, and due-repayment queries. It validates correct HTTP status codes, UUID response shapes, and multi-provider isolation.

### Indexer Bitcoind Runtime (`apps/indexer/test/system/`)

`bitcoind-runtime.integration.test.ts` starts a real bitcoind regtest node and runs a deposit → claim lifecycle through the indexer's `BlockProcessor`, using actual Bitcoin transaction construction via `btc-locker`. This is the lowest-level proof that script spend paths and on-chain state transitions are consistent with each other.

### Full Protocol Lifecycle (`test/system/e2e-no-node/`)

`final-lifecycle.scenario.ts` (entry via `index.test.ts`) drives a multi-party scenario against a running API server using a fake in-process Bitcoin harness:

- **3 users**, **3 FINAL-type programs** across **2 providers**
- **4 deposits**: user 1 → programs A and C; user 2 → program B; user 3 → program C
- All on-chain deposit transactions arrive in a single block
- Providers claim, register due distributions, and the indexer reconciles through `DISTRIBUTION_CONFIRMED`
- Validates correct HTTP status codes at each step, lifecycle state accuracy, and multi-provider isolation

### Bitcoin API Runtime (`test/system/bitcoinapi-runtime/`)

Smoke test verifying health endpoints (`/health/live`, `/health/ready`) are responsive when the API is started in `bitcoinapi` mode (using Bitcoin API as the UTXO provider rather than a local node).

## Notable Functional Test Outcomes

### Staking Script Paths (btc-locker)

- Timelock scripts correctly enforce `OP_CHECKLOCKTIMEVERIFY`; spending before expiry throws `TimelockError`
- Escrow scripts enforce the two-path `OP_IF/OP_ELSE` structure; both keys are validated as secp256k1 compressed points
- PSBT signing is tested end-to-end: key derivation → script construction → PSBT creation → signing → extraction
- Deposit transactions enforce non-empty inputs, fee address/amount co-presence, and a protocol fee output when configured
- Distribution transactions handle mocked fee rates and reject underfunded inputs

### On-Chain Lifecycle (btc-yield indexer)

- Deposit, claim, distribution, and withdrawal state transitions all progress correctly through the full `BlockProcessor` / `TransactionProcessor` pipeline in integration tests
- H-5-01 (spoofed provider-claim) and H-5-02 (spoofed withdrawal) fixes are covered: input outpoint binding and destination/amount binding are now validated and tested
- H-5-03 (attacker-controlled deposit output) fix is covered: canonical output scripts are enforced
- C-5-01 (distribution AML invariant) fix is covered: strict 1:1 output-to-allocation mapping rejects any non-depositor output

### API Contract (btc-yield API)

- All DTO validators are tested under `forbidNonWhitelisted: true` — invalid addresses, cross-network addresses, out-of-range amounts, and unknown fields all return 400
- PSBT semantic validation (M-5-03 fix) is tested: malformed or structurally invalid PSBTs are rejected before reaching service logic
- Multi-provider / multi-program isolation is verified in the full lifecycle E2E scenario

## Known Gaps & Outstanding Items

- The btc-locker `bitcoin-api.ts` HTTP client has low automated unit coverage by design; live path validation depends on the `bitcoinapi-runtime` system test and the `bitcoind-runtime` integration test
- Withdrawal and settlement phases beyond `DISTRIBUTION_CONFIRMED` are not covered by the current E2E lifecycle scenario (noted as out of scope in the scenario header)
- The demo server in `btc-locker` exposes keypair generation endpoints that are explicitly flagged as requiring authentication before production use; those endpoints have no automated auth tests

# Testing Results — Bridging

## Overview

This report summarises the test results for the Cardano on-chain
bridging component implemented in `charms-cardano`. It covers test outcomes
as of the May 2026 milestone and the remediation trajectory observed following an
independent code review conducted in May 2026.

The repository contains a small set of Plutus V3 validators (~150 lines of
validator code) written in Aiken, implementing a withdraw-0 routing pattern that
delegates per-version authorisation logic for the Charms metaprotocol on
Cardano. All tests are executed with `aiken check` using Aiken's built-in test
runner. The framework does not emit line/branch coverage percentages; coverage
evidence takes the form of explicit positive and negative unit tests for each
decision point in the validator logic.

---

## How the Repository Maps to Features

| Feature Area | Module | Role |
|---|---|---|
| Cardano transaction routing | `validators/main.ak` | Asserts beacon NFT presence on the last reference input and delegates to the versioned staking validator whose script hash is recorded on that UTxO |
| V1 authorisation (ICP signature) | `validators/scrolls.ak` | Requires a specific ICP verifier key hash in `extra_signatories`; permits staking-credential registration via `RegisterCredential` |
| V2 authorisation (Groth16 zk-SNARK) | `validators/staking_groth16.ak` | Extracts a `SpellDatum` from the last transaction output, verifies version binding, and runs BLS12-381 Groth16 proof verification |
| Beacon NFT minting | `validators/free_mint.ak` | Permissioned minting policy: mints are gated on a designated signer key hash present in `extra_signatories` |
| Beacon helpers | `lib/charms-cardano/beacon.ak` | `BeaconParts` / `BeaconDatum` types; `beacon_asset_name` construction |
| Spell serialisation | `lib/charms-cardano/charms.ak` | `SpellDatum` / `NormalizedSpell` types; `cbor_serialize` (SHA-256 of CBOR → single BLS12-381 scalar); `extract_spell` (inline-datum-only) |
| Numeric utilities | `lib/charms-cardano/utils.ak` | `bytearray_to_list`, `bytearray_to_int` |

## Notable Functional Test Outcomes

### Routing Safety (`validators/main.ak`)

- All three rejection paths identified in the independent code review (Section 8.4) are now covered by explicit negative tests
- `expect has_nft(...)` correctly panics when the reference input carries no beacon NFT
- `expect Some(charms_validator) = ref_input.output.reference_script` correctly panics when the field is `None`
- `pairs.has_key(Withdraw(Script(charms_validator)))` correctly returns `False` when the matching `Withdraw` redeemer is absent, confirmed by a non-`fail` test using `!main_impl(...)`

### V1 Authorisation (`validators/scrolls.ak`)

- `extra_signatories` check is exercised across all three meaningful states: correct signer, wrong signer, and no signers
- The `publish` handler is not directly unit-tested but is structurally identical to the `scrolls` pattern and is covered by code review

### V2 Authorisation (`validators/staking_groth16.ak`)

- The full validator path exercises `extract_spell` (inline datum required), version binding, `cbor_serialize`, and `groth_verify` in a single test
- The direct `groth_verify_direct_pass` / `groth_verify_direct_fail` pair isolates the BLS12-381 pairing logic from the validator harness, confirming that the `ak-381` library correctly accepts the valid proof and rejects a structurally plausible but cryptographically invalid one
- The `mock: True` field of `NormalizedSpell` is included in the serialised public input, so a mock proof and a non-mock proof have different proof statements and cannot be substituted

### Beacon NFT Minting (`validators/free_mint.ak`)

- Minting is now gated on a designated `permissioned_vk`; the validator is no longer free-for-all
- Positive and negative cases both covered
